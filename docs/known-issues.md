# 알려진 문제 (범위 밖으로 등록된 것)

작업 중 발견했으나 해당 작업의 범위에서 의도적으로 제외한 문제를 모은다.
「나중에 보자」로 흘려보내지 않기 위한 목록이다. 각 항목은 **무엇이 문제인지**,
**왜 그때 고치지 않았는지**, **고칠 때 무엇을 조심해야 하는지**를 적는다.

---

## 1. 「주거 안정」이 기본 HARD인데 정량 효과가 없다

`HOUSING_STABILITY`는 기본 강도가 HARD이지만, 이 목표가 HARD라고 해서 계산이
달라지는 지점이 없다. 사용자는 「반드시 지키기」를 골랐는데 시뮬레이션은 그것을
읽지 않는다.

**등록 시점** 2026-08-22, 목표 제약 계층 작업 착수 전 (회장님 지시)
**왜 미뤘나** 정량 규칙을 새로 정의해야 하는데, 그것은 계산 정합성 수정이 아니라
새 금융 규칙 설계다. AGENTS.md의 「임의의 금융 제도를 새로 만들지 않는다」에 걸린다.
**조심할 것** 규칙을 만들기 전에 「주거 안정이 HARD라는 것이 무엇을 뜻하는가」를
먼저 정해야 한다. 기본값을 SOFT로 낮추는 것도 선택지다.

## 2. 목표 금액이 계획에서 씨앗으로 깔리는데, 체감 커브가 그것을 구조적으로 미달시킨다

`RetirementGoalSelector.tsx:30-37`이 목표의 `targetValue`를 계획의 기준 생활비에서
자동으로 깐다. 그와 **별도로** 앱은 체감 커브 프리셋(`front_loaded`, `care_heavy` 등)을
제공한다. 커브가 지출을 0.86/0.76배로 떨어뜨리므로, HARD 생활비 목표를 고른 사용자는
**사용자가 진술한 적 없는 숫자**로 영구 미달 판정을 받는다.

실측 (추천 후보 수, `maxCandidates: 48`):

| 시나리오 | 계층 작업 전 → 후 |
|---|---|
| 기본 데모 + HARD 생활비 350만 | 12 → 3 |
| `front_loaded` + 기대수명 100 | 6 → **0** |
| `care_heavy` + 기대수명 100 | 6 → **0** |

빈 화면은 아니다 — `StrategyOptimizer.ts`가 `no_candidate_survived`를 내고
`StrategyRecommendationCards.tsx`가 원인을 이름 붙여 보여준다.

**등록 시점** 2026-08-22, 목표 제약 계층 작업 중
**왜 미뤘나** 의미론 자체는 옳다(HARD면 HARD다). 대안은 HARD 바닥이 커브를
**들어올리게** 하는 것이고 계층상 일관되지만(커브는 계층 4 선호, 바닥은 계층 1),
저장된 시나리오의 **결과**를 실제로 바꾼다. 「기존 저장 시나리오의 의미와 결과를
조용히 변경하지 않는다」가 우선한다. 또한 씨앗 정책은 제품 결정이지 계산 결정이 아니다.
**조심할 것** 씨앗을 고치는 쪽(목표 금액을 사용자가 명시적으로 정하게)이
계산을 고치는 쪽보다 부작용이 작다.

## 3. HARD 바닥이 있는 계획에서 「지속가능 생활비」의 정의가 열려 있다

`findMaxSustainable`은 이제 탐색 중 `hardSpendingFloor`를 걷어낸다. 걷어내지 않으면
탐색이 **정확히 바닥으로 수렴해** 사용자 입력을 측정값이라며 되돌려줬다.

세 가지 답이 가능하고, 스펙은 가운데를 명령한다:

| | 값 | 뜻 |
|---|---|---|
| 바닥 유지 | 2,500,000 | 입력의 메아리 — 무가치 |
| **바닥 제거 (현재)** | **1,181,250** | 선호를 지킬 때의 용량 |
| 런타임 동등 | 3,446,596 | 엔진이 실제로 한도를 깨고 도달하는 값 |

(연금 5억, 세제 한도 ON, 60→70세 측정)

**등록 시점** 2026-08-22
**왜 미뤘나** 세 번째 값은 바닥 입력에 의존해 순환하고, 탐색 재설계가 필요하다.
**조심할 것** 현재 값은 런타임 실제 수령액보다 **낮게** 보인다. 배너는 탐색값이 곧
계획의 지출인 `max_sustainable`에서만 미달을 말하도록 좁혀 두었다 — 그 게이트를 풀면
원장이 반증하는 문구가 다시 뜬다.

## 4. 부동소수점 잔여(약 1e-9원)가 허위 HARD 미달을 만든다

`CashFlowPipeline.ts:52-58`의 반올림이 `unmetSpending`에 1e-9원 수준의 잔여를 남긴다.
`hasSpendingShortfall`은 의도적으로 엡실론이 없으므로(`spendingShortfall.ts:11-14`)
이 잔여가 `HARD_SPENDING_SHORTFALL` → `hardConstraintsSatisfied = false` → 후보 탈락으로
이어진다. 기준 계획 1,080개 중 **16개**에서 발생. 실측 사례: 기대수명 68 / 목표 600만 /
`tax_first`에서 평생 미충족 합계 9.3e-10원인데 HARD 목표가 「위반」으로 보고된다.

**등록 시점** 2026-08-22 (병합 기준 `3ab8a89`부터 존재 — 신규 회귀 아님)
**왜 미뤘나** 병합 기준부터 있던 문제이고, 고치면 모든 골든이 움직일 수 있어
자체 검증 사이클이 필요하다.
**조심할 것** `meetsSustainabilityGoal`에 엡실론을 넣는 것은 **답이 아니다** —
그 판정이 이동하면 `max_sustainable`이 흔들린다. 금액 단위가 원이므로
**발생원에서 원 단위로 반올림**하는 쪽이 옳다.

## 6. 서로 다른 두 성공률이 화면에 나란히 뜬다

`DashboardSection.tsx:224`는 `goalSuccessProbability`(목표 대비, 월 1만원 엡실론 있음),
`ShortfallSummaryCard`는 `spendingSuccessRate`(계획 대비, 엡실론 없음)를 보여준다.
서로 다른 질문에 답하므로 값이 어긋날 수 있고, 사용자에게는 모순으로 보인다.
AUDIT-003에서 거짓 불변식은 제거했지만 **화면상의 증상은 그대로**다.

**등록 시점** 2026-08-22
**왜 미뤘나** 두 술어를 통일하면 보고되는 확률이 바뀐다 — 계산 변경이라 별도 검증이 필요하다.
**조심할 것** 통일보다 **라벨을 명확히 하는 것**이 먼저일 수 있다.
두 숫자는 «틀린» 것이 아니라 «다른 것을 재는» 중이다.

## 8. 추천 카드 세 장이 실은 두 개를 뜻한다 — 효과 없는 「달라지는 점」

안정형과 균형형이 목표 달성 확률도 기말자산도 **17자리까지 동일**한데, 균형형에만
「자산 인출: 일반계좌 우선 인출 → **ISA 우선 인출**」이 붙는다.

측정 (`auditReportCase.json`, 51/60/90세, 월 300만, ISA 보유, 실제 파이프라인):

```
GENERAL_FIRST vs ISA_FIRST — 연도별 계좌별 인출액이 «모든 해»에 동일. 처음 갈리는 해: 없음.
goalSuccessProbability = 0.37300000000000000  (양쪽)
endingAssets           = 14850409.590985352   (양쪽)
```

표시 반올림이 아니다. 원인은 ISA가 은퇴 기간에 «존재하지 않는다»는 것이다 —
`maturityYears: 3`이라 마지막 만기가 59세이고, `SimulationEngine.ts:1116-1139`가 ISA를 0으로
만들어 연금으로 넘긴다. `:1089`가 은퇴 후 납입을 멈추므로 60~90세 내내 잔액이 0이고,
`WithdrawalEngine.eligibleAccounts`가 아예 뺀다. **ISA_FIRST는 빈 자리의 순서를 바꾼다.**

두 카드의 유일한 실제 차이는 «알파벳 순서»다. 어느 카드가 어느 정책을 받을지가
`id.localeCompare`로 정해지고(모든 비교자가 동점이라 거기까지 흘러내려간다),
`GENERAL_FIRST` < `ISA_FIRST`라서 안정형엔 인출 변경이 없고 균형형에 「→ ISA 우선」이 붙는다.

결함 위치는 `strategyFieldMap.ts:215-217`이다. `differs`가 enum 값만 비교하고 «그 변경이
무슨 일이라도 하는지»는 보지 않는다. 그래서 카드와 PDF가 효과 없는 변경을 권하고,
「적용」을 누르면 그것이 계획에 실제로 기록된다.

**등록 시점** 2026-08-22
**커밋 `31dad53`은 무관하다** — 두 정책 모두 명시적으로 지정되어 있어 그 커밋 전에도 ISA는
등록됐다. 그 커밋이 바꾼 것은 «정책 미지정» 경로뿐이고, 그 경로는 지금도 GENERAL_FIRST와
결과가 다르다(기말자산 2,556,810.57 대 0).
**조심할 것** `differs`를 결과 기반으로 바꾸면 카드마다 시뮬레이션이 한 번씩 더 든다.
`StrategyOptimizer`에서 Monte Carlo «전»에 결정론적 결과로 후보를 중복 제거하고,
동점을 접을 때 사용자의 «현재 정책»과 맞는 후보를 우선하는 쪽이 비용이 작다.
그러면 유령 「자산 인출」 줄이 저절로 사라진다.
