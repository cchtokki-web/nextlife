# 평가 파이프라인 순서

## 한 줄 정의

전략 추천은 후보 생성 → 사전 HARD 제거 → 결정론적 시뮬레이션 → 목표별 평가 → 사후 HARD
제거 → 결정론적 순위화 → Monte Carlo 검증 → 페르소나 추천의 순서로 진행하며, 이 순서를
임의로 뒤집지 않는다.

## 계약

- 「현재 계획은 항상 기준 후보에 포함한다. HARD 사전·사후 검증, 결정론적 순위화, Monte
  Carlo 검증, 페르소나 추천의 순서를 임의로 뒤집지 않는다.」(`AGENTS.md` 현행 제품 계약)
  이 순서를 구현하는 곳은 `StrategyOptimizer.optimize()`(`src/core/strategy/StrategyOptimizer.ts`
  467행 docstring: "Coordinates generation → HARD pruning → simulation → goal evaluation →
  deterministic ranking → ... Monte Carlo validation → 안정형·균형형·여유형 추천")다. 이
  경로는 `src/core/recommendation/RecommendationEngine.ts`의 페르소나 엔진을 거쳐
  Dashboard·PDF·`useAppliedStrategy`/`useStrategyOptimization`(Worker)로 도달한다.
  같은 이름을 쓰는 `src/core/usecases/strategy/RecommendationEngine.ts`의 `recommendStrategy`
  (`useStrategyPipeline` → `LegacyRecommendationEngine` 경로)는 **다른 함수**이고 이 8단계를
  따르지 않는다 — 후보 생성부터 유틸리티 채점까지 완전히 다른 알고리즘이며, 자체적으로 다른
  순서 불변식(추천의 입력은 언제나 센티널 미적용 compiled여야 한다, `runStrategyPipeline.ts`
  33행)을 갖는 별도 파이프라인이다. 이름이 같다고 같은 경로로 읽지 않는다.
- HARD 제약은 서로 다른 정보로 두 번 걸러진다. `HardConstraintFilter.beforeSimulation()`은
  시뮬레이션 전에 정적으로 알 수 있는 사실(HARD 조기은퇴 목표의 은퇴 나이)만 거르고, SOFT
  목표는 거르지 않는다. `afterEvaluation()`은 시뮬레이션·목표평가 결과에서만 알 수 있는
  현금흐름·기말자산 제약을 사후에 거르며, `hardConstraintFailures` 목록 하나만을 탈락 여부의
  근거로 삼는다(불리언 `hardConstraintsSatisfied`는 상세 목록이 비어 있을 때만
  `HARD_UNSPECIFIED`를 합성하는 보조 신호다). (`HardConstraintFilter.ts` 26~58행)
- 결정론적 shortlist 기본값은 12개다(`shortlistLimit`, `StrategyOptimizer.ts` 556행).
- Monte Carlo는 두 단계다. shortlist를 기본 200회(`screeningTrials`)로 선별하고, 페르소나
  승자만 다시 골라 기본 3,000회(`config.trials`)로 확정한다. 화면·PDF에 나가는 숫자는
  언제나 확정 단계의 것이다 — 선별 단계 숫자는 순서를 가리는 용도로만 쓰고 노출하지 않는다.
  (`StrategyOptimizer.ts` 556~572행, 598~644행)
- 선별과 확정 모두 같은 seed(`config.seed`)로 돈다 — 같은 입력이면 같은 후보 순서, 같은
  최종 확률이 재현된다. (`StrategyOptimizer.ts` 565행 주석 "common random numbers, seeded by
  config.seed")
- 최종 후보는 최대 3개, 페르소나(안정형·균형형·여유형)당 하나다(`finalistLimit` 기본값 3,
  `StrategyOptimizer.ts` 641행). 조건을 충족하는 서로 다른 후보가 부족하면 3개보다 적을 수
  있다 — 항상 3장이 나오는 것은 정상 계약이 아니다.

## 흔한 위반

사후 HARD 판정을 불리언 하나와 실패 목록 하나, 두 값으로 따로 보던 시절의 사고다. 커스텀
평가 엔진이 `hardConstraintsSatisfied: false`만 주고 `hardConstraintFailures`는 비워 두면,
후보는 탈락하는데 탈락 사유는 없어 디버그 출력이 "N개 탈락, 사유 {}"가 됐다.
`HardConstraintFilter.afterEvaluation()`이 이 두 입력을 하나의 판정으로 합쳐 그 상태를
없앴다 — 상세 목록이 있으면 불리언이 무엇이든 상세를 따르고, 상세가 없는데 불리언만 거짓이면
`HARD_UNSPECIFIED`를 합성해 사유 없는 탈락을 만들지 않는다. 탈락 여부 자체는 오직 이 함수의
반환 배열 길이 하나에서만 정해진다. (`HardConstraintFilter.ts` 39~45행 주석)

## 근거

- 코드: `src/core/strategy/StrategyOptimizer.ts`의 `optimize()`(467행 이하), `HardConstraintFilter`
  호출부(`beforeSimulation` 502행, `afterEvaluation` 526행), Monte Carlo 선별·확정(556~644행);
  `src/core/strategy/HardConstraintFilter.ts`의 `beforeSimulation()`·`afterEvaluation()`;
  `src/core/recommendation/RecommendationEngine.ts`의 페르소나 배정
- 테스트: `src/tests/core/strategy/StrategyOptimizer.test.ts`의 "선별은 낮은 시행 수로 하고,
  화면에 나가는 숫자는 전체 시행으로 다시 구한다"(286행) — shortlist 12개가 전부 200회로
  선별되고 페르소나 승자만 1,000회로 재확정되며, 두 단계 모두 seed 42가 그대로 전달됨을
  검증한다. 이 순서가 바뀌면(예: 12개 전부를 1,000회로 돌리거나, 선별 숫자가 화면에 새면)
  `trialCounts.filter((t) => t === 200)`가 12가 아니게 되거나
  `recommended.candidate.monteCarlo.goalSuccessProbability`가 선별 확률(0.4)로 나와 실패한다.
  `src/tests/core/strategy/HardConstraintFilter.test.ts`는 `beforeSimulation()`이 HARD
  조기은퇴만 걸러내고 SOFT는 통과시키는지(113행), `afterEvaluation()`이 불리언·상세 조합
  세 가지 모두에서 사유 없는 탈락을 만들지 않는지(81~110행)를 검증한다 — 사전 필터가
  SOFT까지 거르도록 바뀌면 마지막 테스트가, 사후 판정이 다시 불리언만 보도록 바뀌면 앞의
  세 테스트가 실패한다.
