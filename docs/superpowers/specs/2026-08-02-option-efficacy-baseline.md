# Phase 0 — 전략 옵션 효용성 실측 baseline

측정일: 2026-08-02 / 커밋: `14fcd8a` (develop)

개선 작업 착수 전 "옵션을 바꾸면 결과가 실제로 달라지는가"를 수치로 고정한 문서다.
이후 모든 변경은 이 표를 before로 삼는다.

## 측정 방법

`useStrategyPipeline`과 **동일한 배선**을 헤드리스로 재현했다.

```
compileStrategy(params) → recommendStrategy(compiled.params, engine, compiled.utilityConfig)
                        → applyAiSentinels(compiled, recommendation)
                        → engine.run(effective.params, effective.utilityConfig)
```

픽스처는 `RecommendationEngine.performance.test.ts`의 `worstCaseParams`
(55세 / 은퇴 61세 / 기대수명 95세, 목표 월 300만원, 자산 2종 · ISA 1좌 · IRP 6억 · 국민연금 월 100만,
물가 0% 실질 기준). 모든 격자 차원이 살아 있는 케이스다.

한 축만 바꾸고 나머지는 `DEFAULT_RETIREMENT_STRATEGY`로 고정했다. 판정 기준:

- 🔴 **완전 no-op** — 모든 선택지에서 연도별 총자산 곡선이 비트 단위로 동일
- 🟠 **현금흐름 무영향** — 곡선은 갈리지만 고갈나이/기말자산/은퇴점수가 동일
- 🟢 **살아있음** — 서로 다른 곡선이 2종 이상

## 축별 상세

### 🔴 상속 전략 — 완전 no-op (진단대로)

| 값 | 고갈 | 기말자산 | 은퇴점수 | 효용점수 |
|---|---|---|---|---|
| spend_all | - | 643,585,970 | 96 | 72 |
| leave_some (기본값) | - | 643,585,970 | 96 | 72 |
| maximize | - | 643,585,970 | 96 | **82** |
| target_amount (5억 지정) | - | 643,585,970 | 96 | **81** |

**"모두 사용"과 "최대 상속"이 정확히 같은 금액을 남긴다.** 바뀌는 것은 효용 점수뿐이고,
그마저도 `spend_all`과 `leave_some`은 완전히 동일하다. 사용자가 5억을 남기겠다고 지정해도
인출 계획이 조금도 달라지지 않는다.

→ 계획 B5(`withdrawalPlan.assetFloor` 도입)가 겨냥하는 지점. **before 값: 곡선 1종.**

### 🟠 목표 우선순위 — 5택 중 4택이 동일

| 값 | 고갈 | 기말자산 | 은퇴점수 | 효용점수 |
|---|---|---|---|---|
| lifetime_spending | - | 643,585,970 | 96 | 79 |
| tax_minimization | - | 643,585,970 | 96 | 71 |
| wealth_maximization | - | 643,585,970 | 96 | 71 |
| bequest_maximization | - | **733,933,786** | 96 | 53 |
| ai_recommended (기본값) | - | 643,585,970 | 96 | 72 |

**"평생 생활비 최대화"와 "자산 최대화"가 완전히 같은 계획을 만든다.** 유일하게 갈리는
`bequest_maximization`도 직접 배선된 결과가 아니라, 목적함수가 바뀌어 격자 argmax가
움직였고 그중 **국민연금 개시 나이 한 축만** 센티널로 복사된 부수 효과다.

즉 진단서에 쓴 "목표 우선순위는 자산곡선을 전혀 안 바꾼다"는 **부정확했다**. 정확히는
"5택 중 4택이 동일하고, 나머지 1택은 국민연금 나이 하나를 통해서만 반영된다".
계획 B5의 "출력 폐기가 결함" 분석은 이 실측으로 오히려 강하게 뒷받침된다.

→ **before 값: 곡선 2종 / 5택.**

### 🆕 사적연금 인출 — 5택 → 2결과 (계획에 없던 발견)

| 값 | compileStrategy가 만든 월 목표액 | 한도제한 | 기말자산 | 연금세 합계 |
|---|---|---|---|---|
| tax_first (한도의 100%) | 1,250,000 | true | 1,876,097,869 | 21,945,000 |
| growth_first (한도의 50%) | 625,000 | true | **1,876,097,869** | **21,945,000** |
| minimum (한도의 25%) | 312,500 | true | **1,876,097,869** | **21,945,000** |
| spending_first | undefined | false | 733,933,786 | 198,735,069 |
| ai_optimized (기본값) | undefined | false | 733,933,786 | 198,735,069 |

**`withdrawalRatio` 1 / 0.5 / 0.25가 결과에 아무 영향이 없다.** 컴파일 단계에서는 목표액이
정확히 세 배 차이로 만들어지는데, 엔진 결과는 마지막 자리까지 같다.

**원인** — 저율과세 한도 캡 `monthlyPensionPreTaxLimitRemainingKRW`가 정상 인출
(`SimulationEngine.ts:633-637`)과 **후행 인출**(`:748-752, :757-758`)에서 **공유**된다.
생활비 부족분이 남아 있으면 후행 인출이 남은 한도를 끝까지 채운다:

```
tax_first   : 정상 125.0만 → 잔여한도 0     → 후행 0      → 합계 125만
growth_first: 정상  62.5만 → 잔여한도 62.5만 → 후행 62.5만 → 합계 125만
minimum     : 정상  31.25만 → 잔여한도 93.75만 → 후행 93.75만 → 합계 125만
```

즉 `withdrawalRatio`는 **인출 순서만 바꾸고 총액을 바꾸지 않는다.** 부족분이 남지 않는
(= 자산이 매우 많거나 생활비가 매우 적은) 시나리오에서만 차이가 난다.

화면 문구는 세 옵션을 서로 다른 전략으로 설명하지만("절세 우선" / "자산 성장 우선" /
"최소 인출"), 일반적인 은퇴 시나리오에서는 **전부 같은 동작**이다.

→ 계획 Track B에 항목 추가 필요. **before 값: 5택 → 2결과.**

## 계획 반영 사항

1. **Track B에 항목 추가** — 사적연금 `withdrawalRatio`가 후행 인출과 한도를 공유해
   무력화되는 문제. 인출 비율을 "총액 목표"로 만들려면 후행 인출이 정상 인출의 목표액을
   초과하지 못하도록 별도 캡이 필요하다.
2. **B6(강건성 모드)의 우선순위 상향** — 기본값이 모든 실제 시나리오보다 낙관적이라는
   것은 단순한 미구현이 아니라 사용자를 오도하는 상태다.
3. **진단서 정정** — 목표 우선순위는 "완전 no-op"이 아니라 "5택 중 4택 동일". 완전
   no-op은 상속 전략 하나뿐이다.
